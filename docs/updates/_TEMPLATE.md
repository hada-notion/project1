# vX.Y — (한 줄 제목)

- 날짜: YYYY-MM-DD
- 이전 버전: vX.(Y-1)
- 요약: (사용자에게 보이는 변화를 1~2줄로)
- 매뉴얼 영향: 없음(확인: 원본 메뉴얼에서 찾아본 낱말) / 있음 → 아래 "메뉴얼 갱신" 항목

> 작성 규칙
> - 항목마다 유형을 표시한다.
>   - **AI 자동**: 운영 소유자가 전체 계획을 한 번 승인하면 운영 AI가 승인된 범위에서 코드 반영·테스트·커밋·배포·결과 확인까지 순서대로 진행한다. 별도 담당자 검토나 항목별 재승인은 요청하지 않는다.
>   - **운영자 직접**: AI가 할 수 없지만 운영자가 할 수 있는 일. AI가 멈추고 "운영자 안내문"을 바탕으로 운영자의 상황에 맞게 설명한다.
> - 항목은 실행 순서대로 번호를 매기고, 앞 항목이 끝나야 하는 경우 "선행 조건"에 적는다.
> - **운영자 직접** 항목은 가능하면 앞쪽이나 뒤쪽에 모아서 AI 작업이 중간에 자주 끊기지 않게 한다.
> - 줄 번호는 쓰지 않는다. "찾을 원문 → 바꿀 원문"을 정확히 적는다.
> - 노션 DB는 ID가 아니라 **DB 이름·역할**로 적는다. 운영 AI가 운영 DB에 매핑해 연결한다.
> - **Notion 항목은 "바꾸는 순서"가 아니라 그 항목의 최종 모양으로 쓴다.** 수식·버튼 값은 바꾼 뒤 전체 원문, 바꾸기 전 원문, 바뀐 뒤 지문([노션-지문.json](../기준/노션-지문.json)의 항목 이름과 값)을 함께 적는다. 운영의 현재 값이 둘 중 어느 것과도 다르면 멈추고 [원본 요청](../기준/적용-절차.md#3-원본-요청-흐름)을 한다. 이렇게 쓰면 몇 버전을 건너뛴 학원도 같은 결과가 된다.
> - Notion을 바꾸는 패치는 원본을 다시 스캔해 `docs/기준/노션-지문.json`을 같은 커밋에서 갱신한다([적용 절차](../기준/적용-절차.md) 4장).
> - Supabase 주소, 키, 토큰, 노션 ID 같은 환경별 값과 비밀값은 적지 않는다. 필요한 Secret은 **이름만** 적는다.
> - 학생·수업 등 업무 데이터의 삭제나 대량 변경이 포함되면 적용 전 영향 범위를 별도로 보고하고 AI·관리자 작업 규칙 16-4에 따라 승인을 다시 확인한다. 기존 삭제·공개 범위·토큰 재발급·대량 전송·코드 및 DB 구조 변경의 안전 규칙을 유지한다.
> - **운영 AI가 되물을 만한 것은 미리 답해 둔다.** 필요한 Notion 속성(이름·타입·초기값), 값의 출처, 이미 있을 때의 처리(건너뜀 등)를 항목에 적는다. 기준 자료가 누락되거나 실제 환경과 다르면 추정한 기본값으로 변경하지 않는다. 기준 코드·운영 환경 불일치, 검증 실패, 권한 제한이 발생하면 해당 작업을 중단하고 차이와 재개 조건을 보고한다. 권한이나 보호 규칙을 우회하지 않는다.
> - 전체 계획(바뀌는 내용·영향 범위·리스크·코드 배포 여부)은 처음 한 번 승인받는다. 이미 확인된 승인 범위에서는 항목별 재승인을 요청하지 않는다. 마이그레이션·속성 추가도 승인된 계획에 포함하며, 업무 데이터 삭제·대량 변경의 별도 승인 규칙은 유지한다.
> - **메뉴얼은 패치와 같이 간다.** 속성·버튼·탭·화면·동작 이름이나 쓰는 순서가 바뀌면, 그 이름으로 원본 Notion 메뉴얼을 찾아 같은 작업 안에서 고치고 이 문서에 "메뉴얼 갱신" 항목(페이지·절, 찾을 문구 → 바꿀 문구)을 넣는다. 코드만 바뀌어도 화면에 보이는 결과가 바뀌면(예: 리포트 표시) 해당한다. 고칠 곳이 없으면 "없음(확인: 찾아본 낱말)"으로 무엇을 찾아봤는지 적는다. 나중에 메뉴얼만 따로 맞추는 패치를 만들지 않기 위한 규칙이며, `v2.7.17`부터 회귀 가드가 이 줄을 검사한다.
> - **항목이 여러 개인 버전(작업 중 버전)은 맨 위에 "운영 적용 순서" 표를 둔다**(단계: 미리 할 일 → 칸 추가(배포 전) → 코드 배포 → 버튼·수식·자동화(배포 후) → 레이아웃 → 확인 → 옛 것 정리 → 메뉴얼). 원본에서 기능을 하나 더할 때마다 항목 본문과 이 표를 **같은 커밋에서** 고친다. 오래 걸리는 외부 작업(카카오 템플릿 심사 등)은 "미리" 단계에 둔다.
> - **작업 중에 넣었다 뺀 것**은 항목 본문에서 지우고 "운영에 적용하지 않음" 한 줄로 모은다. **원본에서 겪은 실수**(수식 오류, 자동화 덮어쓰기 등)는 최종 원문에 고친 상태로 넣고, 부록 "작업 중 생긴 실수와 최종 반영"에 한 줄씩 남겨 운영에서 되풀이하지 않게 한다.
> - **바꾸기 전 원문은 바꾸는 그때 기록한다**(어사이드·브라우저 결과에 원문이 오면 바로 부록에 옮긴다). 나중에 다시 읽으려면 원본이 이미 바뀌어 있어 구할 수 없다.
> - 이미 나간 버전에서 사소한 보정(속성 1~2개 누락, 오탈자 등)만 필요하면 새 마이너 버전(vX.Y) 대신 패치 버전(vX.Y.Z)으로 올린다. 파일명은 `docs/updates/vX.Y.Z.md`, "이전 버전"은 바로 앞에 나간 버전(마이너 또는 패치)을 적는다. 이미 배포된 버전 파일의 주제를 다른 내용으로 덮어쓰지 않는다 — 과거 버전 문서를 고쳐야 할 만큼 틀렸다면 새 패치/마이너 버전을 따로 만든다.

## 원본 작성·관리 흐름

원본의 이슈 접수부터 GitHub 반영까지는 [패치·이슈 관리 안내](../패치-이슈-관리.md)를 따른다. 수정·테스트·검수 후 패치노트를 확정한다. DB 상태 변경은 배포 승인이 아니며 자동 업로드를 실행하지 않는다. 이 안내는 운영에 원본 관리 DB 생성이나 원본 저장소 수정을 요구하지 않는다.

## 항목 N. 메뉴얼 갱신 (매뉴얼 영향이 "있음"일 때)

- **유형**: AI 자동(운영 메뉴얼 페이지 수정은 운영 소유자 승인 후, 16-8 9번)
- **대상**: 메뉴얼 > (페이지) > (절). 원본 메뉴얼 반영 여부를 적는다.
- **찾을 문구 → 바꿀 문구**: 문단마다 정확한 원문 쌍. 새 문단은 넣을 위치(앞 문단의 원문)를 적는다.
- **찾을 문구가 없을 때**: 그 문단만 보류하고 기록한다. 위치를 추정해 새로 넣지 않는다.
- **검증**: 바뀐 뒤 문구와 원문으로 대조한다.
