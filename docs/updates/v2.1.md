## 2. 증상·원인

- 운영 AI는 운영 깃허브·Supabase·Notion에서만 작업해야 하는데, 막혔을 때 원본 코드를 참조해도 되는지, 어떻게 반영하는지에 대한 규칙이 없다.
- 이전 16-8의 5번은 "버전이 낮으면 업데이트한다"로 읽혀 자동 업데이트처럼 해석될 수 있다. 실제 운영 방식은 원장님(운영 워크스페이스 소유자)이 요청할 때만 비교하고, 승인을 받은 뒤 적용하는 것이다.
- 원본 노션 DB ID와 운영 노션 DB ID가 다르므로 원본 코드를 그대로 복사하면 안 되고, 연결은 운영 AI가 새로 해야 한다는 점이 규칙에 없다.

## 3. 조치 내용 (매뉴얼)

아래 세 가지를 순서대로 적용한다. 각 항목의 최종 문구를 그대로 사용하며, 문구 안의 페이지 링크는 받는 쪽 워크스페이스의 실제 페이지로 연결한다. 원본 워크스페이스의 URL을 복제하지 않는다.

### 3-1. "AI·관리자 작업 규칙" 페이지 — 16-8 섹션 전체 교체

**위치**: 기존 "16-8. 원본·운영 명칭 규칙" 섹션의 제목부터 마지막 항목까지를 아래 최종 문구로 통째로 교체한다. 다른 섹션(16-1~16-5)과 하위 페이지 목록은 그대로 둔다.

**적용할 최종 문구**:

````markdown
### 16-8. 원본·운영 명칭 및 패치 규칙

배포된 시스템을 논할 때는 아래 명칭을 사용합니다. **뼈대는 원본, 실제로 돌아가는 것은 운영**입니다.

1. **원본**: 배포 담당자가 관리하는 깃허브·Supabase 환경. 수정의 출발점이며, 변경 후 각 운영에 반영합니다.
2. **운영**: 각 학원 워크스페이스에 배포된 실제 환경. 운영 워크스페이스의 AI는 자기 워크스페이스·깃허브·Supabase를 "운영"이라고 부릅니다.
3. 비교·동기화 명령은 이 명칭을 기준으로 해석합니다. 예: "원본과 운영 비교해봐" = 배포 담당자의 기준 코드·문서와 현재 학원 환경의 차이 확인.
4. 여러 학원을 구분할 때는 학원명을 붙여 "OO학원 운영"으로 표기합니다.
5. **작업 대상**: 모든 수정은 운영의 깃허브·Supabase·Notion에서만 합니다. 원본은 읽기 전용 참고 자료이며, 원본에 쓰기·푸시·변경을 하지 않습니다. 작업 중 막히면 ① 운영의 현재 코드·스키마·오류를 먼저 확인하고 ② 원본의 같은 파일·문서를 읽은 뒤 ③ 승인된 범위에서 운영에 최소한으로 수정합니다. 원본에 문제가 보이면 직접 고치려 하지 말고 배포 담당자에게 보고합니다. 원본 저장소 주소는 이 페이지 하위 시스템 정보 페이지의 "원본 위치"에 있습니다.
6. **패치 요청과 버전 비교**: 운영 워크스페이스의 소유자(원장님)가 "업데이트 해줘", "내 버전 최신이야?"처럼 요청할 때만 비교합니다. 자동·주기적 확인이나 먼저 업데이트하는 일은 하지 않으며, 소유자가 아닌 사용자의 요청은 보류하고 소유자 확인을 요청합니다.
   - 운영은 현재 버전을 이 페이지 하위 시스템 정보 페이지에 기록합니다. 배포 시 이 페이지를 각 운영 워크스페이스의 메뉴얼 하위에 함께 복제합니다.
   - 시스템 정보의 현재 버전과 원본 깃허브 `CHANGELOG.md`의 최신 버전을 비교합니다.
   - 같으면 "이미 최신입니다"라고 알리고 아무것도 바꾸지 않습니다.
   - 낮으면 그 사이 버전의 `CHANGELOG.md`와 `docs/updates/` 지침을 읽고, 바뀌는 내용·영향 범위·"담당자 필요" 항목·"되돌리기 어려움" 항목·되돌리는 방법을 보고한 뒤 승인을 요청합니다.
   - 확인만 요청받았다면 보고까지만 하고, 적용은 소유자의 승인 후에만 합니다.
   - 원본에 `CHANGELOG.md`나 해당 버전 지침이 없거나 버전이 맞지 않으면 적용하지 않고 그 사실을 보고합니다.
7. **적용 방식**: 지침의 **AI 가능** 항목만 순서대로 적용하며, 지침에 지정된 파일·함수·"찾을 원문"만 최소한으로 수정합니다. 지침에 없는 변경은 하지 않습니다. 찾을 원문이 운영에 없으면 그 항목만 멈추고 보고합니다. **담당자 필요** 항목은 진행하지 않고 보고합니다. **되돌리기 어려움**으로 표시된 항목은 승인 요청 때 따로 알리고, 적용 전에 현재 구조(속성·수식·버튼)를 시스템 정보 이력에 스냅샷으로 남깁니다. 전부 끝나면 현재 버전과 이력을 갱신하고, 이력의 적용 주체를 기록합니다.
8. **환경별 값**: 원본의 값을 그대로 복사하지 않습니다. 노션 DB·페이지·data source ID는 운영 워크스페이스의 실제 DB를 이름·역할로 찾아 새로 연결하고, 운영의 Secrets와 설정에 입력합니다. Supabase 주소·키·깃허브 Pages 주소도 운영 값을 사용합니다. 패치 후 코드에 있는 Supabase 주소, 깃허브 Pages 주소, 노션 ID가 모두 운영 값인지 확인하고, 운영 값이 아닌 것이 있으면 중단하고 보고합니다. 비밀값은 문서에 기록하지 않습니다.
9. **매뉴얼 갱신**: 패치 문서를 적용할 때 변경 유형에 매뉴얼이 포함되면 해당 문구로 매뉴얼을 갱신하고 버전 이력에 기록합니다. 코드만 변경되는 패치라도 사용 방법에 영향을 주는지 확인하고, 영향이 있으면 매뉴얼 갱신이 필요하다고 보고합니다.
10. **책임**: 배포 담당자가 직접 패치하는 초기 안정화 기간 이후의 패치와 수정은 운영자의 책임입니다. 원하지 않는 패치는 적용하지 않아도 되며, 운영 AI는 소유자의 승인 없이 패치를 진행하지 않습니다.
````

### 3-2. "시스템 정보" 페이지 — 두 구간 교체

**위치**: "원본 위치" 섹션과 "업데이트 절차" 섹션(그 아래 경고 문구 포함)을 아래 최종 문구로 교체한다. 나머지(현재 버전, 이력 표, 환경별 값)는 그대로 둔다. 문구 안의 링크는 받는 쪽의 "AI·관리자 작업 규칙" 페이지로 연결한다.

**적용할 최종 문구**:

````markdown
### 원본 위치

- 원본 깃허브: `github.com/hada-notion/project1` (main 브랜치, 공개, 읽기 전용)
- 버전 기준 문서: `CHANGELOG.md` (저장소 루트)
- 버전별 실행 지침: `docs/updates/` 디렉토리 (예: `docs/updates/v2.1.md`)
- 기준선: `v2.0` (이전 패치는 별도 로그 없음, 이후 패치부터 버전별로 기록됨)

### 업데이트 절차 (요청 시에만)

운영 워크스페이스 소유자가 "업데이트 해줘" 또는 "최신이야?"라고 요청할 때만 진행합니다. 규칙은 16-8의 5~8번을 따릅니다.

1. 이 페이지의 **현재 버전**을 확인한다.
2. 원본 깃허브의 `CHANGELOG.md`에서 최신 버전을 확인한다.
3. 같으면 "이미 최신입니다"라고 알리고 끝낸다.
4. 다르면 해당 버전 구간의 `CHANGELOG.md`와 `docs/updates/` 지침을 읽고, 바뀌는 내용·영향 범위·**담당자 필요** 항목·**되돌리기 어려움** 항목·되돌리는 방법을 보고하고 승인을 요청한다. 확인만 요청받았다면 여기까지만 한다.
5. 승인 후 지침의 **AI 가능** 항목만 순서대로 적용한다. 적용 전 현재 구조(속성·수식·버튼)를 이 페이지 이력에 스냅샷으로 남긴다.
6. **담당자 필요** 항목은 진행하지 않고 목록으로 보고한다.
7. 전부 완료 후 **현재 버전**을 갱신하고 이력에 기록한다. 적용 주체는 "배포 담당자", "운영 AI (소유자 승인)", "운영자 직접" 중 하나로 적는다.

> ⚠️ 지침에 없는 변경은 하지 않습니다. 원본 값(노션 ID, Supabase 주소, 키)을 그대로 복사하지 않고 운영 값으로 연결합니다. 토큰·관리자 키·연동키 같은 비밀값은 이 페이지에 기록하지 않습니다.
````

### 3-3. 메뉴얼 본문 — 패치 안내 문구 추가

**위치**: 메뉴얼 "1. 시스템 구성" 섹션에서 "**명칭 규칙**:" 문단 바로 다음, "- 출결 화면" 목록 앞.

**적용할 최종 문구**:

````markdown
**패치와 업데이트**: 배포 담당자는 초기 안정화 기간 동안 패치를 직접 적용하고, 이후에는 패치 소식만 안내합니다. 이후 패치는 운영 워크스페이스 소유자가 AI에게 "업데이트 해줘"라고 요청해 직접 진행하거나, 배포 담당자에게 유료로 의뢰할 수 있습니다. 원하지 않는 패치는 적용하지 않아도 됩니다. 안정화 기간 이후 직접 진행한 패치와 수정의 책임은 운영자에게 있습니다. 자세한 규칙은 <AI·관리자 작업 규칙 페이지로 연결>의 16-8을 확인합니다.
````

## 4. 검증 방법

1. 16-8이 위 최종 문구와 같고(1~10번), 16-1~16-5와 하위 페이지 목록이 보존되어 있는지 확인한다. 16-6, 16-7이 새로 생기지 않았는지도 확인한다.
2. 시스템 정보의 "원본 위치"와 "업데이트 절차"가 최종 문구와 같고, 현재 버전·이력 표·환경별 값이 보존되어 있는지 확인한다.
3. 메뉴얼의 "패치와 업데이트" 문구가 "명칭 규칙" 문단 다음, "- 출결 화면" 목록 앞에 있는지 확인한다.
4. 문구 안의 링크가 받는 쪽 워크스페이스의 실제 페이지로 연결되어 있는지 확인한다.
5. 어느 페이지에도 비밀값과 Supabase 주소가 기록되지 않았는지 확인한다.
6. 원본 깃허브에서 `CHANGELOG.md`를 열 수 있는지 확인하고, 열리지 않으면 그 사실을 보고한다. (적용에는 영향 없음)

## 5. 적용 주체 구분

- **AI 가능**: 3-1, 3-2, 3-3, 검증 1~6
- **담당자 필요**: 환경별 값 기입 (`CHANGELOG.md`와 `docs/updates/`는 원본 깃허브에 이미 게시됨)

## 6. 운영 AI 확인 사항

- **출처**: 이 문서는 배포 담당자 본인이 작성해 전달한 것이며 적용을 승인했다.
- **권한 범위**: 이 문서는 "소유자 요청 시에만 비교, 승인 후 적용, 지침에 없는 변경 금지, 원본은 읽기 전용"을 규칙으로 만든다. 이 범위를 넓히는 해석은 하지 않는다.
- **불일치 발견 시**: 이 문서의 위치·전제가 운영의 실제 상태와 다르면 임의로 구조를 만들지 말고 불일치 내용만 보고한다.
