# v2.7.14 — 상태 감시가 학원 자기 메뉴 DB를 찾게

- 날짜: 2026-10-20
- 이전 버전: v2.7.13
- 요약: 상태 감시(`status-watchdog`)가 메뉴(학원) DB를 원본의 데이터소스 id로 고정해 두어, 운영 학원에서는 메뉴 감시가 매번 실패했다. 그래서 메뉴 [다음주 수업 일괄 생성]이 "작업중"으로 멈춰도 자동 회수되지 않았다. 이제 실행할 때 그 학원 워크스페이스에서 이름이 "메뉴(학원) DB"인 데이터소스를 찾아 쓴다.
- 매뉴얼 영향: 없음
- 변경 유형: Edge Function 1개 수정(`status-watchdog`), 공용 파일 1개 추가. 마이그레이션·Secrets·Notion·화면 변경 없음.

---

## 항목 1. 상태 감시 함수 교체

- **유형**: AI 자동
- **선행 조건**: 없음
- **변경 이유·증상**: 운영 학원의 인테그레이션은 원본 메뉴 DB를 볼 수 없어 메뉴 대상 조회가 실패하고, `status-watchdog` 로그에 `[status-watchdog] 메뉴 sweep 실패`가 남는다. 메뉴의 "상태"가 "작업중"에 멈춰도 "타임아웃 복구"로 바뀌지 않는다.
- **대상 코드**: 원본 `main`과 같게 맞춘다.
  - 추가: `supabase/functions/_shared/menuDataSource.ts`, `supabase/functions/_shared/menuDataSource_test.ts`
  - 교체: `supabase/functions/status-watchdog/index.ts`
  - `.github/workflows/deploy-supabase-functions.yml`: 통째로 바꾸지 않는다(학원마다 Supabase 지역 주소가 다르다). "Test individual textbook ownership and class lookup" 단계의 `deno test` 줄 끝에 `supabase/functions/_shared/menuDataSource_test.ts`를 붙인다.
  - 찾을 원문 (앵커): `status-watchdog/index.ts`의 `const DS_MENU = "0dcba040-586b-83c8-9974-07588b9ab04d"`. 없으면 이미 적용된 것이다.
- **환경별 값**: 없음. 메뉴 DB는 이름으로 찾는다. 같은 워크스페이스에 휴지통이 아닌 "메뉴(학원) DB"가 둘 이상이면 메뉴 감시만 건너뛴다. 그럴 때는 Secret `DATA_SOURCE_MENU_ID`에 이 학원 메뉴 DB의 데이터소스 id를 넣으면 그 값을 쓴다(선택).
- **필요한 Secret (이름만)**: 없음(선택 `DATA_SOURCE_MENU_ID`)
- **Notion 변경**: 없음
- **마이그레이션 / 재배포**: 마이그레이션 없음. `main` 반영 시 배포 워크플로가 `status-watchdog`을 재배포한다.
- **검증**:
  1. `deno check supabase/functions/status-watchdog/index.ts`, `deno test --allow-env supabase/functions/_shared/menuDataSource_test.ts`, `bash scripts/check-known-regressions.sh` 통과.
  2. 배포 후 5분 안에 `status-watchdog` 로그에 `메뉴 sweep 실패`가 더 나오지 않는다. "데이터소스를 찾지 못해 건너뜀"이 나오면 같은 이름 DB가 둘 이상인지 확인한다.
- **실패 시 대처**: 세 파일을 이전 버전으로 되돌려 재배포한다. 업무 데이터는 바꾸지 않는다.
