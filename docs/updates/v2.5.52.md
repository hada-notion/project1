# v2.5.52 — 학사일정 가져오기 중복 생성 방지

- 날짜: 2026-10-12
- 이전 버전: v2.5.51
- 요약: 학사일정 가져오기는 한 번에 4건씩 이어서 처리한다. 실행 중 Notion이 요청을 거부(429)해 다시 시도할 때, 방금 만든 일정이 Notion 데이터베이스 조회에 몇 초 늦게 나타나 같은 일정을 한 번 더 만들 수 있었다(원본 천왕중 "축제" 2026-09-18 2개). 그러면 다음 단계가 "NEIS 동기화키 중복"으로 멈췄다. 만든 일정을 실행 기록에 바로 남겨 재시도가 먼저 확인하게 했다.
- 매뉴얼 영향: 없음
- 변경 유형: Supabase 함수(`sync-school-calendar`), 마이그레이션 1개. Secrets·Notion 변경 없음.

---

## 항목 1. 중복 일정 정리 (이미 생긴 경우만)

- **유형**: 운영자 직접
- **선행 조건**: 없음
- **운영자 안내문**
  - 왜 필요한가: 같은 일정이 두 개 있으면 함수가 어느 쪽을 고칠지 몰라 멈춘다. 학교 페이지의 학사일정 오류에 "NEIS 동기화키 중복"이 보일 때만 해당한다.
  - 어디서: 일정 DB의 "전체 학사일정" 보기에서 그 학교의 같은 이름·날짜 일정
  - 무엇을: 두 개 중 나중에 만들어진 것 하나를 지운 뒤 학교 페이지의 [학사일정 가져오기]를 다시 누른다(멈춘 곳부터 이어서 처리).
  - 끝났는지 확인하는 방법: 학사일정 처리 상태가 "✅ 완료".

## 항목 2. 함수·마이그레이션

- **유형**: AI 자동
- **선행 조건**: 없음
- **대상 파일**: 신규 `supabase/migrations/20261013040000_neis_run_created_keys.sql`. 수정 `supabase/functions/sync-school-calendar/index.ts`
- **변경 내용**
  - 실행 기록 표 `neis_manual_runs`에 `created_keys`(이번 실행에서 만든 일정의 동기화키 → 페이지 id) 추가. 새 학년도·새 학교 코드로 처음부터 시작할 때만 비우고, 이어서 처리할 때는 유지(`begin_neis_manual_run` 재정의).
  - 일정을 만들면 다음 줄로 넘어가는 기록과 함께 `created_keys`에 남긴다. 재시도 때 Notion 조회에 아직 안 보이는 일정은 이 기록으로 확인하고 페이지를 직접 읽는다(사용자가 지웠으면 새로 만든다).
  - 중복으로 멈출 때 오류에 일정 이름·날짜와 정리 방법을 적는다.
- **환경별 값**: 없음(이 마이그레이션에는 원본 주소가 없어 치환 대상이 아니다)
- **검증**: 함수 배포 후 학교 하나에서 [학사일정 가져오기]를 눌러 "✅ 완료"까지 가는지, 일정 DB에 같은 동기화키 일정이 두 개 생기지 않는지 본다.
- **실패 시 대처**: v2.5.51의 `sync-school-calendar`로 되돌린다. 추가한 칸은 남겨도 동작에 영향 없다.
