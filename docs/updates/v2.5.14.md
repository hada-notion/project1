# v2.5.14 — 웹훅 키 교체 화면

- 날짜: 2026-10-13
- 이전 버전: v2.5.13
- 요약: 관리자 설정 페이지에서 Notion 웹훅 키를 교체할 수 있다. 교체 기간에는 옛 키와 새 키가 모두 동작하고, 옛 키로 들어오는 호출을 함수별로 보여 준다. 남은 버튼을 모두 바꾼 뒤 교체를 완료하면 옛 키가 거부된다.
- 매뉴얼 영향: 있음 → 항목 3
- 변경 유형: 코드·Supabase 스키마(마이그레이션 1개)·관리자 화면·매뉴얼. Secrets·Notion 업무 DB 스키마·업무 데이터 변경 없음.
- 선행 버전: v2.5.12(관리자 보안)의 마이그레이션 3개가 모두 적용되어 있어야 한다. 보안 모드(`ADMIN_SECURITY_ENABLED=true`)가 꺼진 운영에서는 화면에 교체 기능이 보이지 않고 기존 동작이 그대로 유지된다.

> 배경: v2.5.12에서 관리자 비밀번호와 Notion 웹훅 키를 분리했다. 웹훅 키는 평소 그대로 두지만 유출이 의심되면 바꿔야 하는데, 한 번에 바꾸면 Notion 버튼·자동화 수십 개가 헤더를 고칠 때까지 모두 401이 된다. 이번 버전은 두 키를 함께 허용하는 전환 기간을 두어 버튼을 하나씩 옮길 수 있게 한다.

---

## 항목 1. 웹훅 키 교체 서버 기능

- **유형**: AI 자동
- **선행 조건**: 운영 소유자의 전체 계획 승인. v2.5.12 마이그레이션 3개 적용 확인(`20261011010000`, `20261012010000`, `20261012020000`).
- **변경 이유·증상**: 위 배경 참고.
- **대상 코드**
  - `supabase/migrations/20261013010000_webhook_key_rotation.sql` (신규)
  - `supabase/functions/_shared/adminSecurity.ts`: `authorizeKey`가 인증 요청에 함수 이름(`route`)을 함께 보낸다.
  - `supabase/functions/admin-security/index.ts`: `webhook-status`, `webhook-start`, `webhook-finish`, `webhook-cancel` 작업 추가.
- **변경 내용**
  - `hada_security_state`에 `previous_webhook_hash`, `webhook_rotation_started`, `webhook_changed_at` 칼럼 추가. 함수별 호출 집계 표 `hada_security_webhook_usage` 신규(RLS, 직접 접근 차단).
  - `hada_security_command`를 같은 동작 + 교체 작업으로 다시 만든다. 모든 DELETE/UPDATE에 WHERE가 있다(Supabase pg-safeupdate).
  - 시작: 관리자 세션 + 현재 비밀번호 확인. 서버가 48자 무작위 키를 만들어 응답으로 **한 번만** 돌려주고, DB에는 해시만 저장한다. 교체가 이미 진행 중이면 거부한다.
  - 전환 기간: 옛 키·새 키 모두 웹훅 경로를 인증한다. 함수별·키별 호출 수와 마지막 시각을 집계한다.
  - 완료: 최근 7일 안에 옛 키 호출이 있으면 화면에서 한 번 더 확인받는다. 완료 후 옛 키는 거부된다. 자동 만료는 없다.
  - 취소: 현재 비밀번호 확인 후 새 키를 버리고 옛 키만 남긴다.
  - 초기 비밀번호(0000) 상태와 키오스크 세션에서는 교체 기능을 쓸 수 없다. 관리자 비밀번호 변경과 배포 담당자 초기화는 웹훅 키를 바꾸지 않는다.
- **환경별 값**: 없음.
- **필요한 Secret (이름만)**: 없음. 교체 후에는 서버 DB가 웹훅 키의 기준이다. Edge Function Secrets의 `ADMIN_SECRET`(`WEBHOOK_SECRET`)은 첫 초기화 때만 쓰이므로 고치지 않아도 된다.
- **Notion 변경**: 없음
- **마이그레이션 / 재배포**: 마이그레이션 `20261013010000_webhook_key_rotation.sql`. 기존 CI가 함수 전체를 재배포한다. **함수 배포를 먼저 끝낸 뒤 화면(Pages)을 반영한다.**
- **검증**:
  1. 전체 함수 타입 검사, Deno 테스트, PostgreSQL 검사(`tests/admin-security-sql.cjs`), 회귀 가드.
  2. 배포 후 관리자 설정에 로그인해 대시보드에 "웹훅 키 교체" 버튼과 웹훅 상태 문구가 보이는지 확인한다. 실제 교체는 항목 2에서 운영자가 필요할 때만 한다.
- **실패 시 대처**: 교체 중 문제가 생기면 화면의 "교체 취소"로 옛 키만 남긴다. 마이그레이션은 칼럼·표 추가와 함수 교체뿐이며 기존 값을 바꾸지 않는다.
- **매뉴얼**: 항목 3

## 항목 2. 웹훅 키 교체 절차 (필요할 때만)

- **유형**: 운영자 직접
- **선행 조건**: 항목 1 배포. 평소에는 하지 않는다. 키 유출이 의심될 때만 한다.
- **운영자 안내문**
  - 왜 필요한가: Notion 버튼·자동화 헤더의 웹훅 키가 외부에 알려지면 누구나 그 버튼의 기능을 호출할 수 있다.
  - 어디서: 관리자 설정 페이지(`admin_settings.html`) → 로그인 → "웹훅 키 교체".
  - 무엇을:
    1. 현재 관리자 비밀번호를 입력하고 "새 웹훅 키 만들기"를 누른다.
    2. 표시된 새 키를 복사한다. 화면을 벗어나면 다시 볼 수 없다. 채팅·문서·스크린샷에 남기지 않는다.
    3. Notion의 각 DB에서 버튼·자동화의 `x-admin-key` 헤더(또는 본문 `adminKey`)를 새 키로 바꾼다. 대상 목록은 `docs/버튼-웹훅-매핑.md`와 Notion 웹훅 체크리스트를 따른다.
    4. 출석 수동 동기화를 쓰면 GitHub Actions Secret `ADMIN_SECRET`도 새 키로 바꾼다.
    5. 관리자 설정의 "교체 현황"에서 "옛 키 마지막 호출" 칸에 기록이 남은 함수를 확인하고 해당 버튼을 마저 바꾼다. 새로고침으로 다시 확인한다.
    6. 옛 키 호출이 더 이상 늘지 않으면 "교체 완료"를 누른다.
  - 입력할 값의 이름: 새 웹훅 키(화면에서 복사), GitHub Secret `ADMIN_SECRET`(해당 운영만).
  - 끝났는지 확인하는 방법: 대시보드의 웹훅 인증키 항목이 "마지막 교체 ○○"로 바뀌고, 아무 Notion 버튼 하나가 정상 동작한다.
  - 흔한 오류와 대처: 완료 후 어떤 버튼이 401이면 그 버튼의 헤더가 아직 옛 키다. 새 키를 잃어버렸다면 "교체 취소" 후 처음부터 다시 시작한다(이미 새 키로 바꾼 버튼은 옛 키로 돌려야 하므로, 키는 꼭 복사해 둔다).
- **검증**: 교체 완료 후 대표 버튼 1개(예: 보고서 생성)를 실행해 성공하는지 확인한다.

## 항목 3. 매뉴얼 문구

- **유형**: AI 자동
- **선행 조건**: 항목 1을 main에 반영한 뒤. 운영의 해당 페이지와 원문이 다르면 그 문구만 보류하고 보고한다.
- **관리자 비밀번호 안내(1장)**: 웹훅 키 설명 문장 뒤에 다음을 추가한다.

  ```
  웹훅 키는 평소 그대로 둡니다. 유출이 의심될 때만 관리자 설정의 "웹훅 키 교체"로 바꿉니다. 교체하는 동안에는 옛 키와 새 키가 모두 동작하므로, Notion 버튼을 하나씩 새 키로 바꾼 뒤 "교체 완료"를 누르면 됩니다.
  ```

- **키 발급 매뉴얼의 `ADMIN_SECRET` 설명**: "웹훅 키는 첫 보안 설정 때 이 값으로 정해지고, 이후 교체는 관리자 설정 화면에서 합니다. 교체 후에는 이 Secret을 고치지 않아도 됩니다."를 덧붙인다.
