## 1. 증상과 원인

다음 주 수업이 없는 상태에서 금요일 과제를 먼저 만든 뒤 일괄 생성하면, 마감이 다음 월요일이 아닌 다음 금요일에 연결되었다.

- 과제 최초 생성은 다음 출석이 없으면 마감을 비워두었다. 무조건 7일 뒤로 지정하는 기본값 때문이 아니었다.
- 이후 백필 로직은 같은 시간표의 이전 수업을 기준으로 활동을 찾고, 전달받은 새 출석을 그대로 마감으로 기록했다. 월·수·금 시간표 전체에서 가장 가까운 다음 출석을 재선택하지 않았다.
- 시간표 대기열은 실제 수업 날짜순으로 정렬되지 않아 해당 사례에서 금요일 수업이 먼저 생성되었다.
- 활동별 학생 등록이 아니라 학습기록의 첫 등록을 사용하던 부분 때문에 다른 학생 과제까지 한 학생의 출석에 연결될 수 있었다.

## 2. 이번 패치의 변경 내용

### 수업 생성 순서

- 일괄 생성 대상을 실제 다음 수업 날짜·등원시간의 오름차순으로 처리한다.
- 동시간에는 시간표 식별자를 사용해 순서를 일정하게 유지한다.
- 수업 한 건씩 이어서 처리하는 기존 방식과 상태 표시를 유지한다.
- 이미 만들어진 수업의 생성 시각이나 표시 정렬을 소급 변경하지 않는다.

### 학생별 과제 마감

- 각 학습활동의 학생 등록을 기준으로, 원래 출석보다 뒤에 있는 본인의 가장 가까운 출석을 선택한다.
- 같은 요일 시간표에 한정하지 않고 다음 출석을 찾는다.
- 다음 출석이 없으면 임의의 날짜나 다른 학생 출석을 지정하지 않는다.
- 자동 지정한 마감은 더 가까운 다음 출석이 이후 생성되면 다시 계산할 수 있게 한다.
- 미제출·삭제되지 않은 대상만 검토하며, 수동 마감과 자동 출처가 없는 기존 마감은 보존한다.
- 과제 마감 백필은 별도 대기열에서 수행하고, 대상별 처리 후 남은 목록을 저장한다.

### 스키마

학습활동(학원) DB에 내부 추적용 `자동 마감 기준`을 추가한다.

- 타입: 출석(학원) DB를 대상으로 한 단방향 relation, 1건 제한
- 초기값: 기존 기록은 비워둔다. 기존 마감을 근거 없이 자동값으로 간주해 일괄 채우지 않는다.
- 설명: `내부 추적용: 시스템이 마지막으로 자동 지정한 과제 마감 출석. 과제 마감이 이 값과 다르거나 수동으로 비워지면 자동 재계산하지 않습니다. 출처가 없는 기존 마감은 보존합니다. 현재 마감을 수동 고정하려면 이 기준을 비우고 과제 마감을 지정하세요.`
- 자동 처리 허용: 실제 마감·기준 모두 비어 있거나, 실제 마감이 시스템 기준과 같은 경우
- 수동 고정: 자동 마감 기준을 비우고 과제 마감을 지정한다. 현재 마감을 다른 값으로 수정하거나 비워도 기존 자동 기준과 달라져 재계산 대상에서 제외된다.
- 기존 속성·뷰·버튼·웹훅·인증·Secrets는 유지한다. 새 Secret·마이그레이션은 없다.

## 3. 다른 운영 환경 적용 순서

### 항목 1. [AI 자동] 스키마 먼저 적용

1. 운영 소유자 승인 후 현재 구조를 스냅샷으로 남긴다.
2. 운영의 학습활동 DB와 실제 출석 DB 관계를 확인한다. 원본 워크스페이스 ID를 복사하지 않는다.
3. 위 `자동 마감 기준` 속성을 생성한다. 동일 이름·타입·대상·1건 제한이면 건너뛴다. 동명 다른 타입·대상이면 변경을 중단한다.
4. 기존 마감이나 업무 데이터를 일괄 정정하지 않는다. 이번 원본 환경의 확인된 6건 정정은 별도 사례이며 다른 운영에 복제하지 않는다.

### 항목 2. [AI 자동] 코드·테스트 배포

선행 조건: 운영 소유자의 전체 계획 승인 및 항목 1 완료. AI가 승인된 범위에서 코드 반영·테스트·커밋·배포·결과 확인까지 순차 진행한다. 별도 담당자 검토나 항목별 재승인은 요청하지 않는다.

기준 코드·운영 환경이 다르거나 검증 실패·권한 제한이 발생하면 해당 작업을 중단하고 차이와 재개 조건을 보고한다. 업무 데이터의 삭제·대량 변경은 기존 별도 승인 규칙을 따른다.

원본 코드 변경은 GitHub PR #4 또는 기준 커밋에서 반영 커밋까지의 변경분을 사용한다. 운영 코드가 원문과 다르면 무조건 덮어쓰지 말고 차이를 검토한다. 저장소 전체·환경별 설정을 복사하지 않는다.

### 항목 3. [운영자 직접] 운영 확인·권장 사용

- 수업은 항상 실제 수업일보다 1~2주 여유 있게 미리 생성해 둔다.
- 일괄 생성 버튼은 한 번만 누르고 완료 상태를 기다린다. 여유 주차를 확보하기 위해 추가 실행할 때도 앞 작업이 끝난 뒤 진행한다.
- 실제 생성 순서와 화면의 보기 정렬은 다르므로 필요하면 생성 시각·로그를 확인한다.
- 월·수·금 반은 금요일에 만든 과제가 각 학생 본인의 다음 월요일 출석에 연결되는지 확인한다.
- 느리더라도 새로운 수업·출석이 계속 만들어지고 있으면 반복 클릭하지 않는다.
- 중단·오류·출석 누락·중복·잘못된 마감이 발생하면 수업/과제 페이지와 오류 상태·발생 시각을 보존해 검토한다. 부분 실패 뒤 버튼을 다시 누르는 것만으로 누락이 전부 복구된다고 가정하지 않는다.
- 1~2주 선생성은 운영 여유를 확보하는 권장 방식이며, 대규모 처리 위험을 제거하거나 자동 복구를 보장하는 수정은 아니다.

## 5. 알려진 한계와 보류 결정

기능 테스트 통과와 대규모 처리 안정성 보장은 구분한다.

- 수업 한 건 처리 제한은 70초, 일괄 체인 제한은 30분이다. 한 반의 학생 수·처리할 수업 수·API 지연에 따라 중단될 수 있다.
- 시간 초과 래퍼는 내부 작업을 취소하지 않는다. 기존 작업과 재시도가 겹칠 수 있다. 로컬 모의 재현에서 시간 초과 뒤에도 기존 작업이 진행됨을 확인했다.
- 수업 페이지 생성 후 출석이 일부만 생성된 상태에서 중단되면, 다음 시도가 최신 수업 날짜를 기준으로 진행해 누락된 출석을 복구하지 못할 위험이 있다.
- 등록 목록은 첫 100건만 조회한다. 150건의 모의 입력에서 100건만 반환되고 다음 페이지는 읽지 않는 것을 확인했다. 종료된 등록도 연결되어 있으면 이 한도에 영향을 줄 수 있다.
- 생성이 서버에서 처리됐지만 응답이 오류인 모의 상황에서는 재시도로 두 번 생성되었다. 생성 요청의 별도 중복 방지 보완은 이번 패치에 포함되지 않았다.
- Notion relation 쓰기는 요청당 100개 제한이 있다. 한 학생의 백필 후보 과제가 과도하게 쌓이는 경우도 별도 점검이 필요하다.
- 워치독은 15분마다, 작업중 상태가 15분 넘게 지속된 항목을 타임아웃 복구로 바꾼다. 누락 수업·출석을 재생성하는 장치는 아니다. 이미 오류인 항목은 이 회수 조건에 포함되지 않는다.
- 과제 마감 워커는 10분마다 대기열 항목을 처리하는 별도 안전망이 있다. 타임아웃 복구·오류 상태까지 모두 자동 재시도하는 것은 아니다.
- 개별 시간표 실패 뒤에도 나머지 체인이 진행되며 메뉴가 완료될 수 있으므로, 메뉴 완료만으로 모든 수업의 출석 완성을 단정하지 않는다.

운영 결정: 예시 데이터가 적어 당장 대규모 실사용 테스트는 어렵다. 수업을 항상 1~2주 미리 생성하도록 권장하고, 학생별 청크·중단 지점 재개·중복 방지·등록 목록 페이지네이션·완료 판정 보완은 지금 적용하지 않는다. 실제 오류가 발생하면 해당 사례와 로그를 확보하여 후속 패치로 검토한다. 이 문서 작성으로 기존 제한·워치독·재시도 로직을 변경하지 않는다.

## 6. 적용 기록·복구 원칙

- 이번 원본 환경: 스키마는 AI가 적용, 코드 업로드·커밋·병합은 운영자가 직접 수행, 검수·문서는 AI가 수행했다.
- 다른 운영은 항목 1~3을 승인된 범위에서 별도로 적용한다. 이번 완료 기록을 다른 학원의 적용 완료로 간주하지 않는다.
- 기존 시스템 정보의 전체 현재 버전 v2.2는 유지한다. 중간 버전 전체 적용 여부를 이번 패치만으로 확정하지 않는다.
- 이상 발생 시 새 일괄 작업을 중단하고 스냅샷·상태·오류를 보존한다. 이미 생성된 업무 데이터를 무조건 삭제하거나 다른 학생 관계로 일괄 치환하지 않는다.
- 코드 롤백과 실제 데이터 복구는 구분한다. 코드 롤백만으로 기존 잘못된 마감·출석이 되돌아가지 않는다. 자동 마감 기준 속성은 기록 보존을 위해 즉시 삭제하지 않는다.
