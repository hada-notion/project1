# 새 학원(고객) 이식 체크리스트

> 이 문서는 하다 학원관리 시스템을 **다른 학원(고객)에게 새로 세팅**할 때 쓰는 체크리스트입니다.
> 목표는 (1) 이 저장소를 그 학원 소유 GitHub 저장소로 복제, (2) 그 학원 전용 Supabase 프로젝트 생성,
> (3) 그 학원의 Notion 워크스페이스 연결까지 빠짐없이 끝내는 것입니다.
>
> 공통 기능과 환경별 연결값을 구분해야 합니다. 웹 화면의 연결값은 학원별 설정 파일 `hada_config.js` 한 곳에 있고(v2.5.63), pg_cron 마이그레이션에는 아직 환경별 값이 남아 있습니다.
> 아래 값들은 **학원마다 반드시 새로 채워야** 합니다. 하나라도 빠뜨리면 그 학원의 데이터가
> 기존 학원(원본) 것과 뒤섞이거나 조회/발송이 조용히 실패할 수 있습니다.

## 사용 대상·하드코딩 원칙

배포받은 **운영 워크스페이스의 소유자와 운영 AI**가 사용하는 최초 설치·인수 체크리스트입니다. 공통 절차는 재사용하되, 운영마다 다른 DB·주소·권한 연결은 최초 1회 확인합니다. 원본 저장소는 읽기 전용 참고이며 수정·배포 대상은 자기 운영 환경뿐입니다. 전체 계획을 한 번 승인받은 뒤 AI 자동 항목을 끝까지 진행하고, 직접 처리할 수 없는 설정만 운영자 직접으로 안내합니다. 업무 데이터 삭제·대량 변경은 별도 승인과 기존 안전 규칙을 유지합니다.

문서에는 실제 운영 주소·DB ID·키를 고정하지 않습니다. 값은 운영 환경에서 확인하며, 비밀값은 Secrets·Vault·설정 화면에 입력하고 채팅·문서·공개 Git에 기록하지 않습니다. 신규 환경별 상수를 소스에 추가하는 것을 기본 절차로 삼지 않습니다.

**학원별 설정 파일:** 웹 화면(학부모 리포트·키오스크·법정 서류·학교 검색·관리자 설정)은 Supabase 주소와 anon 공개 키를 저장소 루트의 `hada_config.js` 한 파일에서 읽습니다(v2.5.63). 이 파일은 학원마다 다르며 **원본 업데이트를 적용할 때 덮어쓰지 않습니다.** 나머지 화면 파일은 원본 최신본으로 통째로 바꿔도 됩니다. 회귀 가드가 화면 파일에 주소·키가 다시 들어오는 것을 막습니다.

**현행 제한:** pg_cron 마이그레이션에는 아직 Supabase 주소가 들어 있고 아래 스크립트가 처음 한 번 바꿉니다. 하드코딩 없는 배포가 필수 조건이면 마이그레이션 부분은 미충족으로 보고합니다. 존재하지 않는 설정 파일·API를 가정하지 않습니다.

## 실제 진행 순서와 완료 기준

이 문서의 번호는 설정 항목별 분류이며 실행 순서는 다음과 같습니다.

1. **복제본·권한·기준 확인 [AI 자동]:** 운영 시스템 정보와 배포 담당자가 전달한 버전·브랜치·커밋 전체 해시를 확인한다. 복제된 Notion DB를 이름·역할로 찾고 스키마·관계·data source·연결 권한을 확인한다. 예시 학생·연락처·토큰·로그·원본 링크는 검토하며 별도 승인 없이 삭제하지 않는다.
2. **환경 연결 [AI 자동·운영자 직접]:** 운영 전용 프로젝트·저장소·Notion 인테그레이션을 준비한다. 아래 1~3의 설정은 실제 운영 값과 대조한다. AI가 처리할 수 없는 계정·키·설정 화면은 운영자가 직접 입력하고 AI가 확인 가능한 범위를 검증한다. 학교 기능의 `NEIS_API_KEY`도 확인한다.
3. **운영 배포 [AI 자동]:** 승인된 운영 코드·마이그레이션만 반영하고 기존 CI·배포 결과를 확인한다. 원본 번호 seed·opaque ID 매핑을 그대로 적용하지 않는다. 원본 서비스 호출이나 미해결 필수 조건이 있으면 중단한다.
4. **Notion 연결 [AI 자동·운영자 직접]:** 아래 4의 수식·웹훅·학교 검색·메뉴얼 링크를 운영으로 연결한다. 직접 조회하지 못한 버튼 액션은 미검증으로 표시하고 운영자에게 설정 화면 확인을 안내한다.
4-1. **예시 데이터 비우기 [AI 자동, 소유자 승인]:** 4단계 연결과 발송 없는 버튼 확인을 마친 뒤, 알림톡 키를 넣고 5단계 시험을 하기 전에 GitHub Actions의 "예시 데이터 비우기 (최초 설치 전용)"를 실행한다. 먼저 워크스페이스 이름 없이 실행해 건수를 보고하고, 소유자 승인 뒤 이름을 넣어 다시 실행한다. Notion 예시 데이터와 Supabase 사본·법정 서류 번호를 비우고, 성공하면 작업이 스스로 꺼진다(아래 5장).
5. **시험 [AI 자동·운영자 직접]:** 승인된 테스트 학생·수신처로 등록→시간표→교재·수업·출석→학생별 과제 마감→등하원→보고서·첨부파일→알림톡을 확인한다. 학교 기능과 포함된 법정 서류도 확인한다. 실제 학부모에게 임의 발송하지 않는다.
6. **인수 [AI 자동·운영자 직접]:** 실제 확인한 버전·커밋·완료일·운영 주소·학원명·소유자/패치 요청 권한자·안정화 기간·적용 주체·미검증/보류를 운영 시스템 정보에 기록한다. 필수 설정과 시험을 마친 뒤 사용한다. 원본 배포 완료를 운영 적용 완료로 대신하지 않는다.

운영 환경이 유지되면 평소에 전체 최초 설정을 반복하지 않습니다. 주소·DB·권한·키가 바뀌거나 패치를 적용할 때 영향받는 항목만 다시 확인합니다. 단계 실패 시 해당 작업을 중단하고 마지막 성공 단계·오류·재개 조건을 남기며 권한·보호 규칙을 우회하지 않습니다.

## 0) 학원별 설정 파일·마이그레이션 초기 치환

학원별 설정 파일 `hada_config.js`(웹 화면 전체가 읽는 Supabase 주소·anon 공개 키)와 pg_cron 마이그레이션 8개(키오스크 오늘 출석 준비 `20261013030000_kiosk_today.sql`, 수업 관리 복사본 예약 실행 `20261014060000_class_room_copy_cron.sql` 포함)는 GitHub Pages가 서버 환경변수를 못 쓰는
구조상 값이 파일 안에 직접 들어갑니다. **저장소를 새로 복제한 뒤, 첫 커밋/배포 전에** 아래
스크립트를 한 번 실행해 이전 학원 값을 이번 학원 값으로 한 번에 바꿉니다.

```bash
python3 scripts/setup-new-academy.py \
  --new-url https://<새 Supabase 프로젝트 ref>.supabase.co \
  --new-anon-key <새 프로젝트 anon key> \
  --new-pages-path <이 저장소의 GitHub 저장소 이름>
```

실행 후 `git diff`로 변경 내역을 확인하고 커밋하세요. (이 스크립트는 GitHub/Supabase Secrets는
다루지 않습니다 — 아래 1)·2)는 별도로 진행합니다.)

### 학교 검색·주소 확인 (스크립트 실행 후에도 직접 대조 필요)

학교 검색 화면도 `hada_config.js`의 주소로 `school-api`를 호출합니다(v2.5.63). 다만 스크립트 실행 완료만으로 환경 연결 완료로 표시하지 않습니다. 운영 학교 검색
화면이 실제로 운영 `school-api`를 호출하는지, 학교 DB의 `학교 검색` 수식이 그
운영의 자체 호스팅 주소를 여는지 `git diff`와 실제 화면에서 별도로 대조합니다. 완료 기준은
운영 Supabase에 `school-api` 함수가 배포돼 있고, 운영 학교 검색 화면에서 검색·연결이 되는 것입니다.
위 하드코딩 원칙·미충족 처리 기준을 유지합니다.

또한 이 스크립트는 README의 저장소 경로를 바꾸지만 GitHub 계정 도메인 전체를 자동으로 바꾸지는 않습니다. 실제 운영 웹페이지 주소·보고서 링크·버튼·자동화·마이그레이션을 대조하고 원본 환경 호출이 남으면 중단합니다. 공통 문서에 실제 값을 추가하지 않습니다.

## 1) 새 Supabase 프로젝트 준비 — GitHub 저장소 Secrets

새 Supabase 프로젝트를 만들고, GitHub 저장소를 그 학원 소유로 복제한 뒤 GitHub Actions 배포가
그 프로젝트를 향하도록 아래 GitHub 저장소 Secrets(Settings → Secrets and variables → Actions)를
설정합니다.

| GitHub Secret 이름 | 용도 |
| --- | --- |
| `SUPABASE_PROJECT_ID` | 새 프로젝트의 ref (배포 대상 지정, cron 워크플로 호출 URL 조립에도 사용) |
| `SUPABASE_ACCESS_TOKEN` | Supabase CLI 배포용 개인 액세스 토큰 (최대 1년 만료, 만료 전 재발급 필요) |
| `SUPABASE_DB_PASSWORD` | 새 프로젝트 DB 비밀번호 (마이그레이션 적용용) |
| `SUPABASE_ANON_KEY` | 새 프로젝트의 anon key (cron 워크플로가 Edge Function 호출 시 사용) |

### 1-1) 연결 문자열 작성 예시 (Session pooler)

`SUPABASE_DB_PASSWORD`는 이 프로젝트 DB 비밀번호이며, Supabase 로그인 비밀번호와는 다른 값입니다. 마이그레이션 적용에 쓰이는 연결 문자열은 아래 규칙을 따릅니다.

- 이 배포 방식은 **Session pooler** 주소를 사용합니다 (Supabase 대시보드 → Project Settings → Database → Connection string → Session pooler 탭에서 확인).
- 연결 문자열의 `[YOUR-PASSWORD]` 자리만 실제 프로젝트 DB 비밀번호로 바꾸고, 앞뒤의 `:`와 `@`는 그대로 둡니다.
- 비밀번호에 특수문자(`@`, `:`, `/`, `#` 등)가 있으면 연결 문자열에 넣기 전 URL 인코딩이 필요합니다.
- 연결 실패는 아래 세 가지로 구분해 원인을 좁힙니다.
  - 네트워크 연결 실패: 주소·포트·방화벽 문제. Session pooler 주소를 쓰고 있는지부터 확인합니다.
  - 비밀번호 오류: `[YOUR-PASSWORD]` 치환이 맞는지, 로그인 비밀번호를 넣은 건 아닌지 확인합니다.
  - 마이그레이션 오류: 연결 자체는 성공했지만 SQL 적용 중 실패한 경우이며, 연결 문제와 구분해 보고합니다.
- 비밀번호가 포함된 연결 문자열은 채팅이나 공개 저장소에 붙이지 않습니다.

## 2) Supabase Edge Function Secrets (대시보드 → Edge Functions → Secrets)

먼저 Notion 쪽에서 이 학원의 각 DB를 준비하고(템플릿 복제 권장) ID를 확인한 뒤 아래 이름
그대로 등록합니다.

> ⚠️ **데이터베이스 ID와 데이터소스 ID는 다른 값입니다.** Notion의 멀티 데이터소스 구조상
> 하나의 DB에 "데이터베이스(페이지) ID"와 "데이터소스 ID" 두 가지 별개 ID가 있고, 서로 유도할
> 수 없습니다. 아래 표에서 `DATA_SOURCE_*_ID` 계열(19개)은 **데이터소스 ID**(`collection://...`
> 형태, DB를 열고 속성 패널이나 API로 확인)를, `NOTION_REGISTRATION_DB_ID`·`NOTION_SEND_LOG_DB_ID`·
> `NOTION_ALIMTALK_CONFIG_DB_ID` 3개는 **데이터베이스(페이지) ID**(그 DB가 인라인으로 들어있는
> 메뉴 페이지를 열었을 때 DB 블록 자체의 URL)를 씁니다. 반대로 넣으면 404로 조용히 실패합니다.

| 관리자 보안 (v2.5.12) | `ADMIN_SECURITY_ENABLED` | `true`로 등록하면 보안 모드 시작. `ADMIN_ALLOWED_ORIGINS` 등록 후, 그 학원 수업이 없는 시간에 등록하고 바로 관리자 설정(`admin_settings.html`)에서 초기 비밀번호 `0000`을 변경. 변경 전에는 키오스크·서류·학교 화면 로그인 불가 |
| 웹앱 | `SITE_BASE_URL` | 예: `https://<계정>.github.io` |

| 라이브러리 (v2.5.120, 선택) | `NL_CERT_KEY` | 국립중앙도서관 ISBN 서지정보 API 인증키(nl.go.kr 회원가입 → ISBN 서지정보 Open API 신청, 승인까지 1~2 영업일). 학원 계정으로 발급한다(원본 키를 나눠 쓰지 않음). 라이브러리 화면 안에서 국내 도서 검색·목차. **없어도 된다** — 교보문고 책 페이지에서 즐겨찾기 [교재 가져오기]로 가져와 [직접 추가]에 붙여넣는다(v2.6.6) |

학습기록(학원) DB의 `단원`은 단원목록(학원) DB와의 관계 속성(양방향 이름 `학습기록`, v2.5.126~127)이고, 버튼 `단원 입력`은 `fill-record-units` 웹훅(웹훅 키)을 부릅니다. 예전 `단원` 수식이 남아 있으면 다른 수식이 쓰지 않는지 확인한 뒤 지웁니다([v2.6 Notion 작업](updates/v2.6-노션-작업.md) N-7).

라이브러리 추가(`library.html` → `textbook-api`)는 두 키 중 하나만 있어도 그 출처로 동작하고, 둘 다 없으면 503입니다. 옛 `ALADIN_TTB_KEY`는 더 쓰지 않습니다(알라딘 OpenAPI 2026-10-30 종료).

코드에는 예전 이름도 남아 있습니다(`NOTION_API_KEY`·`NOTION_SECRET` → `NOTION_TOKEN`, `ALIMTALK_CONFIG_DB_ID` → `NOTION_ALIMTALK_CONFIG_DB_ID`). 새 학원은 표의 이름만 등록합니다.

## 3) Supabase Vault 시크릿

Database → Vault → Add new secret 에서 이름 `sync_queue_admin_key`, 값은 위 `ADMIN_SECRET`과
동일하게 등록합니다. pg_cron 예약 실행(큐 워커 매분, 상태 워치독 15분, 동기화 실패 점검 30분,
과제 마감 백필 10분, 키오스크 오늘 출석 준비 매일 04:00 KST, 수업 관리 복사본 처음 채우기 3분·증분 5분·매일 밤 대조 4개,
라이브러리 복사본 대조 10분)이 모두 이 값으로 인증합니다. 없으면
이 예약 실행이 모두 401로 실패합니다(버튼 웹훅·화면 호출은 영향 없음). 특히 키오스크는 새벽 준비가
없으면 화면을 처음 열 때 준비하느라 첫 출결이 느려집니다.

보안 모드(`ADMIN_SECURITY_ENABLED=true`)를 켠 뒤에는 서버가 이 값을 내부 키로 자동 교체하고 관리자
비밀번호를 바꿀 때마다 함께 갱신합니다. 켠 뒤에는 손으로 바꾸지 않습니다.

## 3-1) 관리자 보안 활성화 (v2.5.12)

1. Supabase Secrets에 `ADMIN_ALLOWED_ORIGINS`를 등록하고, `ADMIN_SECRET`이 Notion 웹훅 헤더와 같은 값인지 확인합니다.
2. 학원 수업이 없는 시간에 `ADMIN_SECURITY_ENABLED`=`true`를 등록합니다.
3. 원장님이 관리자 설정 페이지에서 `0000`으로 로그인해 새 비밀번호를 설정합니다.
4. 키오스크·법정 서류·학교 검색 화면에 새 비밀번호로 로그인하고, Notion 버튼 하나가 동작하는지 확인합니다.
5. 비밀번호 분실 시 배포 담당자가 `scripts/reset-admin-password.py`로 `0000` 초기화합니다. 상세: [v2.6.5 지침](updates/v2.6.5.md) 항목 1.

## 4) Notion 쪽에서 직접 고쳐야 하는 부분 (코드/스크립트로 자동화 불가)

- **등록(학원) DB의 "학생 페이지" 수식**(v2.5.55 전 이름 "안내 링크"): `link(..., "https://<계정>.github.io/<저장소>/student_report.html?token=" + prop("토큰"))`
  형태로 되어 있습니다. 출석(학원) DB의 "학생 페이지"는 이 수식을 등록 관계로 가져오는 롤업이라 따로 고칠 필요가 없습니다. 이 학원의 실제 GitHub Pages 주소로 직접 고쳐야 합니다(Notion 수식이라
  코드 배포로는 안 바뀝니다).
- 각 Edge Function을 호출하는 Notion 버튼·자동화("웹훅 보내기" 액션)를 전부 새 프로젝트의
  URL로 다시 연결하고, 관리자 키가 필요한 함수는 `x-admin-key` 헤더도 이 학원의 `ADMIN_SECRET`
  값으로 다시 넣어야 합니다.
  - 어떤 DB의 어떤 버튼/자동화가 어떤 Edge Function을 호출해야 하는지는 추측하지 말고
    [`docs/버튼-웹훅-매핑.md`](버튼-웹훅-매핑.md) 표를 참고하세요.

## 4-1) 보고서 동기화 흐름 (수정일 → 스캔 → 동기화 → 발송)

새 학원에 이식한 뒤에는 아래 흐름으로 보고서 자동 갱신이 동작합니다. 단계별로 Notion 자동화인지 웹훅인지, 지금 코드가 실제로 지원하는지를 구분해서 확인하세요. 아래 트리거 속성은 v2.5.5·v2.5.6에서 이미 확정된 내용을 그대로 인용한 것이며, 새로 추정한 값이 아닙니다.

| 단계 | 방식 | 트리거/대상 | 코드 지원 여부 | 범위 |
| --- | --- | --- | --- | --- |
| 1. Notion 속성 변경 | Notion 자동화(레코드 편집 시) | 등록 DB: 학생정보, 클래스, 시간표, 진도교재, 등록일, 종료일, 토큰, 링크 비활성화 (v2.5.6 기준) | 배포됨 | 등록 1건 |
| 2. 수정일 기록 | Notion 자동화(속성 편집) | 위 트리거 속성이 바뀌면 `학습정보 수정일`을 현재 시각으로 기록. 상태·처리 시각·오류·메모·버튼 속성과 학습정보 수정일 자체는 트리거에서 제외(무한 루프 방지) | Notion 템플릿에 포함 | 등록 1건의 `학습정보 수정일`만 갱신 |
| 3. 서버가 변경 감지 | 내부 로직 | 수정일과 `마지막 동기화`를 비교 | 지침 확정, 운영별 실제 동기화 로직 연결은 별도 검증 필요 | 등록 1건 |
| 4. 리포트 갱신 | 웹훅 `sync-report-cache` | 등록 "학생 페이지 동기화" 버튼과 동일 함수. 라이브러리·일정 DB는 버튼이 아니라 "레코드 편집 시" 자동화로 연결해야 함 | 배포됨 | 등록 1건 또는 교재/일정 영향 범위 전체 |
| 5. 발송 (필요할 때만) | 웹훅 `send-report`, `send-daily-report` 등 | 리포트 갱신과 별개로 버튼으로 실행(자동 발송 예약 없음) | 배포됨 | 발송 대상별 |

이식 시 1·2단계는 운영 Notion 자동화 화면에서 직접 연결 상태를 확인해야 하며(코드 배포만으로는 자동화가 생기지 않습니다), 3단계 이후는 Edge Function이 처리합니다. 함수별 호출 조건은 [`docs/버튼-웹훅-매핑.md`](버튼-웹훅-매핑.md) 16번 항목을 참고하세요.

## 5) 노션 템플릿 공유

- 배포 담당자가 제공한 최신 검증 템플릿을 복제해 운영 워크스페이스에 준비합니다. 원본 워크스페이스의 고정 페이지 ID를 복제 대상의 ID로 사용하지 않습니다.
- 방금 만든 Notion 인테그레이션을 그 워크스페이스(및 하위 DB 전체)에 연결(공유)합니다.
- **예시 데이터 비우기 (최초 설치 전용)**: 복제한 템플릿에는 원본 테스트용 예시 데이터가 들어 있습니다. 모든 연결(GitHub·Supabase·DB·Secrets·함수)과 발송 없는 버튼 확인을 마친 뒤, **알림톡 키를 넣기 전에** 비웁니다. 예시 학생에는 실제 번호가 들어 있을 수 있으니 비우기 전에는 [보고서 전송]·[안내문 전송]·키오스크처럼 알림톡이 나가는 기능을 시험하지 않고, 법정 서류 화면도 열지 않습니다(예시 학생에게 영구 번호가 발급됨).
  1. GitHub Secrets에 `NOTION_TOKEN`(이 학원 Notion 인테그레이션 토큰)을 넣습니다. `SUPABASE_PROJECT_ID`·`SUPABASE_DB_PASSWORD`는 배포용으로 이미 있습니다.
  2. GitHub → Actions → "예시 데이터 비우기 (최초 설치 전용)" → Run workflow를 워크스페이스 이름 없이 실행합니다. 지우지 않고 Notion DB별 건수와 Supabase 사본 건수, 워크스페이스 이름만 보여 줍니다.
  3. 결과를 확인한 뒤 같은 작업을 2번에서 나온 워크스페이스 이름을 넣어 다시 실행합니다. Notion 예시 데이터를 휴지통으로 보내고(하위부터, 끝에 남은 건수 0 확인), Supabase 사본(수업 관리 사본, 리포트 캐시, 출석 사본, 키오스크 명단, 처리 대기열, 법정 서류 번호 등)을 비운 뒤, 작업을 스스로 끕니다. 관리자 비밀번호·보안 설정과 라이브러리 사본은 남깁니다.
  4. 끝나면 GitHub Secrets의 `NOTION_TOKEN`은 지워도 됩니다(Supabase Secrets의 `NOTION_TOKEN`은 그대로). 이 작업은 설치가 끝난 운영에서 다시 켜거나, 업데이트할 때 다시 추가하지 않습니다.
  - 비우는 DB: 학생·등록·클래스·시간표·수업·출석·진도교재·학습기록·학습활동·보고서·수강료·결제·교재비·교재배부·교재결제·알림톡 발송함·자동화 로그·일정·대시보드·시험·시험정보·성적·학교·강사·근무·자료·업데이트(학원) DB. 남기는 DB: 메뉴·웹페이지·알림톡 설정·과목·학년·교시·라이브러리·단원목록. 기준은 `scripts/clear-example-data.py`의 `CLEAR_DBS`/`KEEP_DBS`, Supabase 표는 `scripts/clear-example-data.sql`입니다.
  - Notion은 휴지통으로 보내므로 되살릴 수 있습니다. 출석 등 페이지가 많으면 15분 안팎 걸리고, 중간에 실패하면 작업이 꺼지지 않으므로 다시 실행하면 남은 것만 지웁니다.
  - GitHub 없이 PC에서 할 때는 `NOTION_TOKEN` 환경변수를 넣고 `python -I scripts/clear-example-data.py`(확인) → `--apply --confirm-workspace "<이름>"`로 Notion만 비울 수 있습니다. 이때 Supabase 사본은 `scripts/clear-example-data.sql`을 따로 실행합니다. 원본 지원 PC에서는 `HADA_SOURCE_WORKSPACE`에 원본 워크스페이스 이름을 넣어 두면 원본에서 `--apply`가 거부됩니다(값은 커밋하지 않음).

## 6) 최종 확인

### 최신 스키마·기능·규모 확인

- 복제한 Notion을 [적용 절차](기준/적용-절차.md) 4장대로 스캔해 원본 지문과 비교하고, "다름·없음"이 0인지 확인합니다. 차이가 있으면 같은 절차의 순서대로 맞춥니다. 운영 적용 기록(`docs/operation-update-history.md`)에는 `기준 일치: <지문 스캔 시각>`을 적고, 과거 버전 표기를 근거 없이 최신으로 바꾸지 않습니다.
- 금요일에 먼저 입력한 과제가 각 학생 본인의 가장 가까운 다음 출석에 연결되는지, 수동 마감이 보존되는지 확인합니다.
- 대규모 수업 생성의 시간 초과·부분 출석 누락·중복·등록 첫 100건 조회 위험은 보완이 보류된 상태입니다. 1~2주 선생성은 권장 사용법일 뿐 안정성·자동 복구 보장이 아닙니다. 새 운영 규모가 한계에 해당하면 사용 시작 전 별도 검토합니다. 실제 오류 시 관련 페이지·상태·발생 시각·로그를 확보합니다.

- GitHub Actions 배포 워크플로우가 성공하는지 확인 (마이그레이션 적용 + 함수 전체 배포).
- 학부모 리포트 웹앱(`student_report.html?token=...`)이 실제로 열리는지 확인.
- 알림톡 테스트 발송 1건으로 Solapi 연동 확인.

### 학습기록·학습활동 본문과 첨부파일 확인

- 새 프로젝트에 `get-report-file` 함수가 배포됐는지 확인합니다. 새 첨부파일 전용 Secret을 만들거나 브라우저에 관리자 키/service-role 키를 넣지 않습니다. 기존 Notion 연결과 보고서 캐시 구성이 필요합니다.
- 테스트 학습기록 본문에 공통 자료, 테스트 학생의 학습활동 본문에 개별 결과를 넣고 해당 등록의 **학생 페이지 동기화**를 실행합니다. 본문·파일 수정이 속성 편집 자동화만으로 항상 반영된다고 가정하지 않습니다.
- 학습·과제·평가별 본문 영역이 올바르게 나뉘고, 이미지·동영상·PDF·일반 파일과 파일명·설명이 표시되는지 확인합니다.
- PDF의 **PDF 열기·인쇄**, 일반 파일의 **파일 열기·다운로드** 버튼을 확인합니다. PDF 인쇄는 열린 브라우저/PDF 뷰어에서 실행하며, 일반 파일은 별도 앱이 필요할 수 있습니다.
- 모바일·데스크톱에서 열기/다운로드를 확인하고, 팝업 차단 또는 파일 오류 시 안내가 표시되는지 확인합니다.
- Notion 업로드 파일 URL의 유효시간이 지난 뒤에도 버튼 클릭으로 최신 URL을 받아 열 수 있는지 확인합니다.
- 유효하지 않은 보고서 토큰(`404`), 다른 보고서 캐시에만 있는 블록(`403`), 접근 허용 캐시 안의 지원하지 않는 블록(`400`)을 테스트합니다.
- 공통 학습기록에 다른 학생의 개인정보·개별 제출물이 섞이지 않았는지 확인합니다. 파일이 공통 자료인지 학생별 자료인지 구분하고, 이미 내려받은 파일은 링크 비활성화로 회수되지 않는다는 점을 안내합니다.

세부 API·보안·회귀 테스트 항목은 [학생 보고서 본문·첨부파일](학생-보고서-본문-첨부파일.md)을 참고하세요.

## 법정 서류 이식 확인

- `legal_documents.html`의 고객 배포 주소/Supabase 연결과 관리자 인증, `get-legal-document-data` 배포를 확인합니다. 주소·연락처·생년월일을 학부모 공개 API에 노출하지 않습니다.
- 고객 워크스페이스의 학생·클래스·등록·출석·수강료·결제 data source ID와 실제 속성/관계를 재확인합니다. DB 페이지 ID를 data source ID로 사용하지 않습니다.
- 번호 관련 마이그레이션/RPC/RLS를 검토합니다. 원본 학원의 학생/결제 번호 seed와 opaque ID 매핑을 그대로 적용하지 않습니다. 신규 고객의 기존 번호가 있으면 충돌 정책부터 확인합니다. 조회가 최초 번호 발급과 Notion 학생 등록번호 보완을 수행할 수 있습니다.
- 전체/반/학생 조회 및 웹·인쇄/PDF·XLSX를 함께 테스트합니다. 교습비=숫자형 수식 청구금액, 결제금액=실제 결제, 기타경비=출력 기본값 0이라는 계약을 유지합니다.
- 원장명 기본 연결/자동 서명/완전한 환불 원부/자동 불변 보관은 미구현입니다. 영수증 등록(신고)번호 칸은 현재 학생 번호이며 공식 의미 확인은 보류 중입니다. 이를 구현 완료·법적 확정으로 안내하지 않습니다.
- 새 고객의 메뉴얼에 법정 서류 사용법과 구조도/API/번호 저장 경계를 함께 옮기고 원본 학원 페이지 링크는 고객 페이지로 다시 연결합니다.
