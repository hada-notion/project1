# 패치·이슈 관리 — 원본 작업 흐름과 GitHub 반영 기준

## 역할과 범위

- Notion의 `패치·이슈 관리` DB는 원본의 이슈 접수·수정·검수·배포 현황판이다.
- GitHub의 `CHANGELOG.md`와 `docs/updates/`는 운영 AI가 읽는 배포 버전·실행 지침의 기준이다. Notion에 문서를 작성하거나 상태만 바꿨다고 GitHub에 반영된 것은 아니다.
- 원본의 배포 완료와 각 학원 운영의 적용 완료는 다르다. 운영별 현재 버전·적용 이력은 해당 운영의 시스템 정보에서 관리한다.
- 이 문서는 원본 배포 담당자를 위한 작업 안내다. 운영 AI에게 원본 저장소 수정 권한을 부여하거나, 각 운영에 이 DB 생성·복제를 요구하지 않는다. 운영 AI는 운영 환경만 수정하고 원본은 읽기 전용으로 참고한다.

## DB 구조

| 속성 | 타입 | 기준 |
| --- | --- | --- |
| 제목 | 제목 | 이슈·패치 이름 |
| 상태 | 상태 | 접수 / 작업 중 / 검수 중 / 배포 전 / 배포 완료 / 보류 |
| 버전 | 텍스트 | 배포할 버전. 버전 없는 관리 문서는 비워둔다 |
| 변경 유형 | 다중 선택 | 코드 / 매뉴얼 / 스키마 / 데이터 |
| 배포일 | 날짜 | 승인된 반영·필요한 검증이 끝난 실제 완료일. 미완료이면 비운다 |
| GitHub 링크 | URL | PR 또는 반영 커밋. 코드·문서 커밋이 다르면 본문에서 각각 기록한다 |

뷰는 상태별 `작업 현황` 보드와 `전체 목록` 표를 사용한다. 새 항목은 `이슈·패치 작성 양식`으로 작성하며, 증상·원인·정확한 수정 범위·승인·사전 스냅샷·검증·복구·커밋·배포 결과를 본문에 기록한다.

## 상태 기준

- **접수**: 증상·요청을 기록한 단계. 수정이나 배포 승인을 의미하지 않는다.
- **작업 중**: 승인된 범위의 수정 단계.
- **검수 중**: 비교·테스트·문서 정합성을 확인하는 단계. 확인할 항목이 남으면 유지한다.
- **배포 전**: 수정·테스트·검수를 마치고 GitHub 반영 준비를 끝낸 단계. 이미 반영한 코드와 남은 문서 작업 등이 있으면 본문에 구분한다.
- **배포 완료**: 승인된 GitHub 반영과 필요한 검증까지 끝낸 단계. 문서만 바꾼 경우 커밋·원문 확인, 실행 코드를 바꾼 경우 필요한 CI·배포 결과도 확인한다. 코드·문서의 필수 반영이 남아 있으면 완료로 표시하지 않는다. 부하 시험 등 미검증·별도 보류 범위는 명시하고 완료를 전체 시스템 검증으로 확대하지 않는다.
- **보류**: 중단 사유·완료 범위·재개 조건을 기록한 단계.

작업 중에는 이슈 기록으로 사용한다. 패치노트는 코드 수정·테스트·검수를 마친 뒤 확정하며, 사전 승인·안전 스냅샷과 구분한다.

## 승인과 진행

1. 소유자가 `배포 전 항목 확인하고 업로드 진행해`처럼 요청하면, 대상 항목·현재 코드와 스키마·기준 문서·승인 범위를 확인한다.
2. 전체 계획에는 바뀌는 내용·영향 범위·리스크·코드 배포 여부를 포함한다. 전체 계획을 한 번 승인받으면 승인된 범위에서 코드 반영·테스트·커밋·배포·결과 확인까지 순차 진행하며 별도 담당자 검토나 항목별 재승인을 요청하지 않는다. 이미 확인된 승인은 반복 질문하지 않는다.
3. 적용 유형은 **AI 자동**과 **운영자 직접** 두 가지다. AI 자동에는 코드 배포를 포함한다. 운영자 직접은 AI가 수행할 수 없는 단계이며 필요한 작업·완료 확인 방법만 안내한다.
4. 업무 데이터 삭제·대량 변경은 영향 범위를 별도로 보고하고 기존 안전 규칙에 따라 승인을 다시 확인한다. 삭제·공개 범위 변경·토큰 재발급·대량 전송 및 코드·DB 구조 변경에 대한 기존 안전 규칙도 유지한다.
5. 기준 자료 부족·환경 불일치·검증 실패·권한 제한이 발생하면 해당 작업을 중단하고 차이·재개 조건을 보고한다. 승인 범위를 넓히거나 권한·보호 규칙을 우회하지 않는다.

**상태 변경 자체는 승인이나 자동 업로드 트리거가 아니다.** 이 안내를 저장하는 것만으로 자동화·Worker·GitHub Actions 트리거가 추가되는 것은 아니다.

## GitHub 반영과 완료 기록

1. 확정된 패치 문서는 `docs/updates/_TEMPLATE.md`에 맞춘다. 확인된 저장소·브랜치·커밋 전체 해시·파일 경로와 정확한 최종 원문을 사용한다.
2. 실제 시스템 패치 배포라면 해당 버전 실행 지침과 `CHANGELOG.md`의 버전·링크를 맞춘다. 원본 내부의 작업 안내·양식 보완만으로 시스템 버전을 올리거나 운영 업데이트를 요구하지 않는다.
3. 환경별 DB·페이지·data source ID, Supabase 주소·키, GitHub Pages 주소는 각 운영의 실제 값을 확인한다. 개인정보·비밀값·내부 업무 데이터를 공개 저장소에 올리지 않는다.
4. 승인된 최소 파일만 커밋한다. 문서와 실행 코드의 커밋·배포 상태를 별도로 기록한다.
5. GitHub 반영 내용을 다시 읽어 원문 일치를 확인한다. 실행 코드 변경은 필요한 테스트·기존 CI·배포 결과를 확인한다. CI 성공만으로 배포 소스 전체 일치를 단정하지 않는다.
6. 실제 확인 범위·미검증·보류 사항·커밋·적용 주체를 DB 본문에 기록한 뒤 완료 기준을 충족하면 배포 완료와 배포일을 갱신한다. 각 운영의 적용 완료나 전체 현재 버전 갱신은 별도 작업이다.

## 실패·복구

실패하면 해당 항목을 중단하고 마지막 성공 단계·오류·재개 조건을 기록한다. 코드 롤백과 업무 데이터 복구는 구분한다. 업무 데이터를 무조건 삭제하거나 관계를 일괄 치환하지 않는다. 기존 스냅샷과 승인된 복구 범위를 사용한다.
